# hello-mlsys

中文 | [English](./README_en.md)

**在 AMD 硬件上学 ML 系统：先建模预测，再上真机验证，最后和 AI 一起把系统设计得更好。**

hello-mlsys 是一个 8 周的社区学习计划。它关注的是**整个系统**，而不是某个工具或某个算子：同一个模型，放在什么硬件上、用什么配置、承载什么负载，能否满足延迟要求，花多少钱、耗多少电。

每周的节奏都一样：先预测，再在 AMD 硬件上实测（从 Ryzen AI 笔记本到 Instinct 云端 GPU），用实测结果修正你的模型，然后决定下一步做什么。后三周，你将和 AI 组队完成几个固定的设计任务，成绩全部在 AMD 硬件上评测。

### 借鉴 MLSys·im 的地方

MLSys·im 的核心观点是：每个 ML 系统最终都会卡在某个瓶颈上（它称之为"墙"）。我们沿用了它的几个教学思路：

- **先说清瓶颈**：每次分析都要指出是哪一类瓶颈：算力、内存带宽、内存容量、通信、软件开销、排队、成本还是能耗。
- **性能公式**：性能可以拆成几项相乘（设备数、峰值、利用率、扩展效率、有效时间占比），任何优化都只改变其中一项。
- **先猜后看**：每个练习都先写下预测，再看结果。课程特意安排了一些"反直觉"的时刻。
- **倒推需求**：从 SLA 出发，倒推需要什么硬件和配置，而不是把所有方案都测一遍。
- **找最敏感的参数**：每个参数都微调一下，看哪个对结果影响最大，下一步就优化它。
- **成本和能耗也是约束**：每 token 成本、每 token 能耗、碳排放从一开始就要算进去。

## 学完你能做到

1. **预测**：运行之前，用估算和模拟器预判延迟、吞吐、显存、成本和能耗。
2. **校准**：实测后分析时间花在哪里，修正模型参数，让下次预测更准。
3. **诊断**：无论是笔记本还是多卡服务器，都能说出系统卡在哪个瓶颈上。
4. **倒推设计**：从 SLA、预算和能耗上限出发，推出所需的硬件和配置，提前排除不可行的方案。
5. **带好 AI 队友**：用证据判断 AI 的分析和方案是否靠谱，识破它"刷指标"的做法，并写清楚每个决定的理由。

## 适合谁

- 会用 PyTorch 跑模型、想从系统层面理解性能的学生和工程师。
- **前置要求**：Python、PyTorch 基础、Linux 基础，能读英文文档；能在 AMD 设备上跑起一个 LLM（不会的话先看 hello-rocm 的环境配置）。**不需要会写算子。**
- **不需要自己有 GPU**：AMD 提供云端算力。
- **时间**：第 1–5 周每周 6–8 小时，第 6–8 周每周约 10 小时。

## 学习方式

每周都是同一个循环：

```
预测（估算 + 模拟器）→ 实测（AMD 硬件）→ 校准（修正模型）→ 决定下一个实验
```

**第一阶段：建模与校准（第 1–5 周）**。每周有阅读、一个实验和一组**案例卡**。每张案例卡是一次真实运行：预测值、实测值、时间线，以及一段 AI 的分析（有时是错的）。你要找出瓶颈，判断 AI 说得对不对，并在揭晓前预测某个改动的效果。这五周下来，你会得到一套针对自己硬件的校准模型，第二阶段直接用。

**第二阶段：与 AI 一起设计（第 6–8 周）**。你和 AI 一对一合作，完成三个固定任务。每个任务的步骤是：

1. **定目标**：自己先定好目标、约束和质量底线。
2. **倒推需求**：动手之前，先算出 SLA 和预算意味着什么。
3. **做规划**：和 AI 一起出方案，采纳、修改或否决它的建议。
4. **筛方案**：用校准过的模型排除不可行的方案。
5. **实测**：在 AMD 硬件上测剩下的方案，每次测之前先写下预测。
6. **迭代**：决定下一个实验，并写下理由。

所有决定都记在**决策日志**里，和结果、预测准确度一起评分。

### 每周详情

<details>
<summary><b>第 1 周：估算与瓶颈</b></summary>

**内容**
- 常见瓶颈：算力、内存带宽、内存容量、通信、软件开销、排队、成本、能耗
- 性能公式：时间 = 工作量 ÷（设备数 × 峰值 × 利用率 × 扩展效率 × 有效时间占比）
- 看规格表估算：prefill 计算量约为 2 × 参数量 × token 数；batch=1 时 decode 速度约为 带宽 ÷ 权重大小
- MLSys·im 入门：硬件库、模型库、第一次 `solve`，以及它能算什么、不能算什么
- 模拟器擅长判断瓶颈、比较方案，但绝对延迟不一定准

**阅读**
- [mlsys-course 第 0 章：系统思维](https://yuuinih.github.io/mlsys-course/modules/00-systems-thinking.html)
- [MLSys·im](https://github.com/harvard-edge/cs249r_book/tree/dev/mlsysim)：入门指南与速查表
- [mlsysbook.ai](https://mlsysbook.ai) 第一卷：导论
- Williams 等，"Roofline: An Insightful Visual Performance Model"（2009）

**实验**：用现成的框架（环境配置见 hello-rocm），分别在个人设备（T1 或 T3）和云端 GPU（T4）上跑一个小 LLM。运行前先按两台设备的算力比和带宽比各预测一次 prefill 和 decode 速度，再实测。

**反直觉**：云端 GPU 算力比笔记本高出很多，但 decode 速度的差距只接近带宽之比。

**案例卡**：3 张入门卡，练习对比预测与实测，并指出瓶颈。

**提交**：一页偏差报告（预测、实测、三个主要原因），以及第一条校准记录：每台设备的实测值 ÷ 预测值。
</details>

<details>
<summary><b>第 2 周：时间都去哪了：在 AMD 上校准</b></summary>

**内容**
- 拆解整个模型的运行时间：计算、访存、框架开销、kernel 启动间隙、空闲
- 模型级利用率：MFU（算力利用率）和 MBU（带宽利用率）
- 用 PyTorch profiler 看模型级时间线。目的是找出时间花在哪，而不是调算子（算子级分析见 hello-gpu 第一部分）
- 在系统层面减少开销：增大 batch、图捕获、`torch.compile`
- 校准：拟合每档硬件的效率参数，用没参与拟合的数据检验，如实报告误差
- 敏感性分析：哪个参数对结果影响最大

**阅读**
- [MLSys·im](https://github.com/harvard-edge/cs249r_book/tree/dev/mlsysim)：效率与实测校准相关文档
- [mlsysbook.ai](https://mlsysbook.ai) 第一卷：硬件加速与基准测试
- PyTorch profiler 文档

**实验**：在两档硬件上，对同一模型扫描不同的 batch 和序列长度。用一半数据拟合校准参数（MFU、MBU、每步固定开销），再预测另一半。把模拟器里缺少的 AMD 设备（如 Radeon、Ryzen AI Max）补进硬件库，每个数字都注明来源。

**反直觉**：在高端 GPU 上跑小 batch，最耗时的往往既不是计算也不是访存，而是开销。

**案例卡**：AI 根据时间线判断一次运行为什么慢，找出它哪里判断错了。

**提交**：校准参数、验证误差，以及每档硬件上最敏感参数的对比表。
</details>

<details>
<summary><b>第 3 周：显存决定方案</b></summary>

**内容**
- 推理显存：权重、KV Cache、激活、运行时缓冲区；KV Cache 随上下文和 batch 如何增长
- 训练显存：权重、梯度、优化器状态、激活；ZeRO/FSDP 分片、激活重计算、LoRA
- 精度不只影响速度：换成 FP8 或 INT4，可能让模型从两张卡变成一张卡，整个方案随之改变
- MoE 模型：总参数量和激活参数量，分别对容量和带宽意味着什么
- AMD 各档内存：消费级显存小；Ryzen AI Max 内存大；Instinct 的 HBM 容量大、带宽高。容量和带宽是两回事

**阅读**
- [mlsysbook.ai](https://mlsysbook.ai) 第一卷：模型优化与训练
- Kwon 等，"Efficient Memory Management for LLM Serving with PagedAttention"（2023）
- Rajbhandari 等，"ZeRO: Memory Optimizations Toward Training Trillion Parameter Models"（2020）
- [MLSys·im](https://github.com/harvard-edge/cs249r_book/tree/dev/mlsysim)：训练显存模型；"How much memory does Llama 3 need?"

**实验**：做一张"什么能放进哪里"表：3 种模型规模（其中一个是 MoE）× 3 种精度 × T2、T3、T4。每一格先预测能否放下、固定上下文下的最大 batch 和 decode 速度，再实测。然后预测一次小规模微调在开/关激活重计算、用/不用 LoRA 时的峰值显存，并实测。

**反直觉**：模型明明"放得下"，并发一高 KV Cache 一涨就爆显存。最大的模型能放进 Ryzen AI Max，但能不能用，要看带宽。

**案例卡**：显存溢出和量化的案例，判断 AI 的解释对不对。

**提交**：完整的表格（预测值和实测值），训练显存预测，以及对主要偏差的解释。
</details>

<details>
<summary><b>第 4 周：推理服务就是排队</b></summary>

**内容**
- 延迟指标：首 token 延迟（TTFT）、每 token 延迟（TPOT）、端到端延迟；p50 与 p99
- Prefill 和 decode 像是共用一块 GPU 的两台机器；连续批处理与分块 prefill
- 排队论基础：利用率、Little 定律、延迟为什么会在拐点附近飙升；有效吞吐（goodput，即满足 SLO 的吞吐）
- 前缀缓存和投机解码的得失：命中率、接受率和额外开销
- 倒推需求：从延迟目标推出需要多少带宽、显存和并发

**阅读**
- Yu 等，"Orca: A Distributed Serving System for Transformer-Based Generative Models"（2022）
- Agrawal 等，"Taming Throughput-Latency Tradeoff in LLM Inference with Sarathi-Serve"（2024）
- Leviathan 等，"Fast Inference from Transformers via Speculative Decoding"（2023）
- [MLSys·im](https://github.com/harvard-edge/cs249r_book/tree/dev/mlsysim)：推理服务容量模型

**实验**：对单卡推理服务做压测，逐步提高请求速率。压测前先用校准过的服务时间和排队模型预测拐点。然后选一个优化手段（分块 prefill、前缀缓存或投机解码），预测它对 p99 和有效吞吐的影响，再实测。

**反直觉**：利用率到 80% 时平均延迟看着还行，p99 却早已超标。

**案例卡**："吞吐上去了，p99 反而变差"之类的案例，评估 AI 给出的三种修复方案。

**提交**：一份报告，包括拐点的预测值与实测值、p99 曲线，以及所选优化手段的效果。
</details>

<details>
<summary><b>第 5 周：扩展、成本与能耗</b></summary>

**内容**
- 集合通信：all-reduce 的 α–β 模型；节点内与节点间的链路
- 张量并行、流水线并行、数据并行、专家并行的取舍；MoE 的热点专家；prefill 与 decode 分离部署
- 扩展效率：卡加到一定数量后，反而会变慢
- 成本：GPU 小时单价、每百万 token 成本，以及为什么利用率决定成本
- 能耗与碳排放：笔记本、Ryzen AI Max 和云端 GPU 的每 token 能耗；电网碳强度
- 大规模下的可靠性：故障率、checkpoint 间隔和有效时间占比

**阅读**
- [mlsysbook.ai](https://mlsysbook.ai) 第二卷：集合通信、大规模推理、可持续 AI
- Shoeybi 等，"Megatron-LM"（2019）；Zhong 等，"DistServe"（2024）
- RCCL 文档与 rccl-tests

**实验**：在多卡节点上用 rccl-tests 测不同消息大小的 all-reduce，拟合 α 和 β，据此预测某个模型加到几张卡时张量并行就不再有收益，再实测两个点验证。在 T1、T3、T4 上测同一个小模型的每 token 能耗，并算出 T4 上每百万 token 的成本。

**反直觉**：加了卡，p99 反而更差。最慢的设备，每 token 能耗不一定最低。

**案例卡**：扩展、成本和能耗相关案例，评估 AI 的建议。

**提交**：一页扩展与成本分析，然后参加阶段测验。
</details>

<summary><b>第 6 周：任务 1，端侧助手</b></summary>

**你要做的**：用校准过的模型设计整个集群，再在 T4 上实测其中有代表性的一部分，证明预测是准的。最后指出限制方案进一步优化的那个约束。

## 考核

**第一阶段**：案例卡自动评分。实验报告要有明确的预测、实测结果和偏差分析。校准参数按验证误差评分。第 5 周的**阶段测验**是一组新的案例卡，须独立完成、不能用 AI，通过后才能进入第二阶段。

**第二阶段**：每个任务看三项：AMD 硬件上的实测结果、你事先写下的预测准不准、决策日志。好的决策日志能看出你：

- 在找 AI 要方案之前，先定好了目标、约束和质量底线；
- 在实测之前，先从 SLA 倒推需求，用模型筛过方案；
- 根据证据采纳或否决 AI 的建议，并发现了它"刷指标"的做法；
- 在宣称任何提升之前，先确认了质量没有下降；
- 记录了预测的准确度，并分析了预测失误的原因。

**关于 AI**：除阶段测验外，都鼓励使用 AI，但你必须能解释和验证自己提交的所有内容。

### 结营要求

- 第一阶段至少完成 4 周的案例卡，并通过阶段测验。
- 第二阶段至少完成 3 个任务中的 2 个，每个都附决策日志。
- 评审另一位学员的决策日志。

**你会得到**：一份由偏差报告、校准参数和决策日志组成的作品集，AMD 实测排行榜上的名次，以及结营证书。优秀学员将在结营展示上分享，并有机会获得 AMD 奖品。
